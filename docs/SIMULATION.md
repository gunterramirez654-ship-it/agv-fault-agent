# 仿真报告：AGV 车队运营与分析链路压测

> 本文所有数字均可用 `./run.sh sim` 复现（固定随机种子 42）。
>
> **数据来源必须区分清楚**：
> - **运营指标**（吞吐、利用率、排队）来自 SimPy 离散事件仿真，是**模型估算**
> - **分析指标**（延迟、token、成功率）来自真实调用，是**实测数据**

---

## 1. 为什么需要仿真

项目在单点能力上已经完成：能对一起故障做检索、判定风险、生成分析报告。

但工程落地要回答的不是"能不能分析一起"，而是：

| 问题 | 需要的指标 |
|---|---|
| 能扛多少量？ | 吞吐量、任务周期 |
| 花多少钱？ | token 消耗、年化成本 |
| 可靠吗？ | 成功率、延迟分位数 |
| 系统瓶颈在哪？ | 资源利用率、排队时长 |

这些指标只能通过**压力测试**获得。在还没有真实部署的情况下，离散事件仿真（DES）是标准做法。

---

## 2. 模型设计

### 2.1 为什么用离散事件仿真，而不是物理仿真

两类仿真解决的问题不同：

| 类型 | 建模对象 | 典型工具 | 产出 |
|---|---|---|---|
| 物理仿真 | 位置、速度、碰撞 | CoppeliaSim / Gazebo | 轨迹、碰撞检测 |
| **离散事件仿真** | 队列、资源、事件 | **SimPy** / AnyLogic | 吞吐、利用率、排队 |

本项目已有 CoppeliaSim 3D 演示（见 README 第 14 节），但它模拟的是**运动**，不产出**运营指标**——CoppeliaSim 里没有"队列"这个概念。因此运营仿真使用 SimPy。

### 2.2 模型要素

```
8 台 AGV
  │
  ├─ 任务循环：等待派单 → 装货 25s → 运往缓存区 40s → 卸货 25s → 返回 40s
  │
  ├─ 电量模型：每任务耗电 1.5%，可用电量 70% ≈ 46 个任务
  │           低于 30% → 前往充电区 → 排队 → 充电 20 分钟
  │
  └─ 待命模型：任务间平均等待 40 秒（指数分布）

2 个充电桩（SimPy Resource，有限资源 → 产生真实排队）

故障注入器（每个区域一个）
  └─ 泊松过程，总故障率 = 每台 AGV 每小时 0.25 次
     → 8 台 × 0.25 × 24h ≈ 48 起/天（实测 42 起）
```

### 2.3 全部模型假设

| 参数 | 取值 | 说明 |
|---|---|---|
| 仿真时长 | 24 小时 | 可配置 |
| AGV 数量 | 8 台 | 可配置 |
| 充电桩数量 | 2 个 | 可配置 |
| 装货耗时 | 25 秒 | 假设 |
| 卸货耗时 | 25 秒 | 假设 |
| 区域行驶时间 | 40~60 秒 | 按区域距离设定 |
| 充电耗时 | 20 分钟 | 假设（0→100%） |
| 每任务耗电 | 1.5% | 标定值，见下 |
| 低电阈值 | 30% | 假设 |
| 待命间隔 | 平均 40 秒 | 假设，代表等待调度派单 |
| 故障率 | 0.25 次/台/小时 | 假设，即每台 AGV 平均 4 小时一次故障 |
| 初始电量 | 30%~100% 随机 | 避免同步伪影 |
| LLM 定价 | 输入 ¥0.5/M，输出 ¥2/M | **假设，以官方页面为准** |

**关于电量参数的标定过程（值得记录）**

初始取值是「每任务耗电 8%」，仿真结果出现明显失真：

```
充电桩利用率 98.6%
平均充电等待 38.8 分钟
最长充电等待 60.0 分钟
```

排查发现：8%/任务 意味着 9 个任务就没电，8 台 AGV 每约 20 分钟就要集体充电一次，
远超 2 个充电桩的承载能力。这是**参数设置制造出来的假瓶颈**，不是真实工况。

改为 1.5%/任务（可用电量支持约 46 个任务，约 1.5 小时充一次电）后，指标回归合理区间。

> 这一步是仿真的常见陷阱：**仿真结果看起来"很有说服力"，但可能只是参数错了。**
> 必须用常识校验每个输出。


### 3.2 故障流（模型估算）

```
事件总数        : 42 起/天
故障率          : 1.75 起/小时
区域分布        : 装载区 8 / 缓存区 11 / 充电区 8 / 避让区 15
```

### 3.3 分析链路（真实测量）

```
分析条数        : 42 条
成功率          : 100.0%（42/42）

召回延迟        : P50  19.2 ms / P95 186.8 ms
LLM 延迟        : P50 2170 ms / P95 4180 ms / P99 7270 ms

Token 消耗      : 输入 49,665 / 输出 12,384 / 合计 62,049
单次平均 token  : 1,477
24 小时成本     : ¥0.0496

```

> 召回 P95 达 186 ms，明显高于 P50 的 19 ms。原因是连续 42 次 LLM 调用后
> 进程内存压力上升，偶发 GC 停顿。生产环境应关注这一点。

## 4. What-if 分析：用仿真做决策

仿真最有价值的用途不是"算出一个数"，而是回答"如果改变配置会怎样"。

```bash
./run.sh sim --what-if
```

```
固定条件：24 小时 / 8 台 AGV / 同一随机种子（故障流一致）

  充电桩   完成任务   充电桩利用率   平均排队   最长排队
  --------------------------------------------------------
    1      3317       97.2%       7.5 分    30.2 分
    2      3477       50.7%       0.3 分     4.8 分
    3      3490       34.3%       0.0 分     0.0 分

每增加一个充电桩的边际收益：
  1 → 2 个：吞吐 +4.8%，平均排队减少 7.3 分钟，利用率 97% → 51%
  2 → 3 个：吞吐 +0.4%，平均排队减少 0.3 分钟，利用率 51% → 34%

建议：
  · 推荐配置为 2 个充电桩（完成任务 3477 个）
  · 1 个充电桩时利用率 97%，已接近饱和，平均排队 7.5 分钟
  · 超过 2 个后收益递减（2 → 3 个仅提升 +0.4%），不建议继续投入
```

**读法**：

- 1 个充电桩是**明确的瓶颈**：利用率 97%，平均排队 7.5 分钟，最长 30 分钟
- 加到 2 个，吞吐 **+4.8%**，排队降到 0.3 分钟——这一刀值得投
- 再加到 3 个，吞吐只 **+0.4%**——边际收益递减，不值得

**这就是仿真给出的决策依据**：不是"越多越好"，而是找到拐点。

## 5. 结论

### 5.1 系统能力

| 维度 | 结论 |
|---|---|
| 吞吐能力 | 每天 42 起事件，折合每小时 1.75 起，单链路完全够用 |
| 延迟 | LLM P95 4.2 秒；因为安全决策由规则系统给出（毫秒级），LLM 延迟不影响 AGV 运行 |
| 可靠性 | 42/42 成功；历史压测中出现的降级均返回规则结论，未丢失安全决策 |
| 成本 | 年化约 ¥18（按 42 起/天、1477 tokens/次估算） |

### 5.2 架构层面的结论

仿真的两阶段设计本身验证了一个架构判断：

> **LLM 不在安全回路里，所以它的延迟不影响运营。**

阶段一的运营时间推进（24 小时）与阶段二的 LLM 耗时（约 2 分钟真实时间）完全独立。
即使把 LLM 换成更慢的模型，AGV 的运营指标也不会变化——因为风险等级与控制动作
在 LLM 调用之前就已由规则系统确定。

### 5.3 局限

- 运营指标是**模型估算**，依赖第 2.3 节的假设；真实部署后应用实际数据替换
- 故障率为假设值，未基于真实运维记录统计
- 未建模：多楼层、充电桩故障、网络分区、任务优先级抢占
- LLM 定价为假设值，实际以官方页面为准

---

## 6. 复现方式

```bash
# 完整运行（含真实 LLM 调用，约 2 分钟）
./run.sh sim

# 只跑运营仿真，不调 LLM（几秒）
./run.sh sim --no-llm

# what-if 对比
./run.sh sim --what-if

# 自定义场景
./run.sh sim --hours 48 --agvs 12 --chargers 3 --seed 7

# 限制 LLM 调用次数（控制成本）
./run.sh sim --max-events 20

# 导出完整 JSON
./run.sh sim --json-out result.json
```
