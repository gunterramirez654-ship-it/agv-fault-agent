# AGV 故障智能分析系统（V1 POC）

> 面向工业 AGV 现场的故障辅助分析系统：**区域优先向量召回** + **规则安全决策** + **LLM 辅助解读** + **全链路日志留痕**。

一个可本地运行的端到端 PoC：从现场事件文本出发，检索历史故障、给出安全结论、生成运维可读的分析报告，并把全过程写入结构化日志。

---

## 1. 解决什么问题

工业现场 AGV 发生故障时，运维人员面临三个现实困难：

| 困难 | 现状 | 本项目的做法 |
|---|---|---|
| **找不到历史案例** | 靠老师傅记忆或翻记录本 | 向量检索，语义匹配历史故障 |
| **判断慢、标准不统一** | 依赖个人经验 | 规则系统秒级给出风险等级与控制动作 |
| **不知道从哪查起** | 排查凭感觉 | LLM 结合历史案例给出可执行排查步骤 |

同时守住一条底线：**LLM 绝不参与安全决策**。

## 2. 架构

```
                    现场事件（感知模块上报）
                              │
                              ▼
        ┌──────────────────────────────────────────┐
        │  vector_store.py   区域优先向量召回        │  ~10 ms
        │  └─ bge_embedding.py  中文向量化          │
        └──────────────────┬───────────────────────┘
                           ▼
        ┌──────────────────────────────────────────┐
        │  规则阈值决策（硬编码，microsecond 级）     │
        │  max_sim → 风险等级 + 控制动作            │
        └──────────────────┬───────────────────────┘
                           │  安全结论已确定，立即可用
                           ▼
        ┌──────────────────────────────────────────┐
        │  agent_harness.py  LLM 可靠性外壳          │  ~2 s
        │  └─ agv_agent.py   调用 DeepSeek          │
        │  输出校验 → 重试 → 降级 → 指标统计         │
        └──────────────────┬───────────────────────┘
                           ▼
        ┌──────────────────────────────────────────┐
        │  simple_logger.py  jsonl 全链路日志        │
        └──────────────────────────────────────────┘
```

**关键设计：快慢分离。** 检索与规则决策在 10ms 内完成，LLM 需要 2 秒。两者解耦，LLM 不可用或超时不阻塞安全决策。

### 模块职责

| 模块 | 职责 | 不做什么 |
|---|---|---|
| `vector_store.py` | 知识库加载、区域优先召回、余弦相似度 | 不打印日志、不调 LLM |
| `bge_embedding.py` | 中文向量化（离线 ONNX） | 不做检索 |
| `agv_agent.py` | 拼 prompt、调模型 | 不感知向量库与日志 |
| `agent_harness.py` | 输出校验、重试、降级、指标、输出预算 | 不做业务分析 |
| `simple_logger.py` | jsonl 落盘 | 不关心日志内容 |
| `test_vector_store.py` | 业务入口、串起全链路 | — |
| `web_demo.py` | 可视化演示服务（标准库 HTTP） | 不修改业务逻辑 |

## 3. 核心创新：区域优先召回（Area-First Retrieval）

### 3.1 为什么需要

工业工厂天然按作业区域划分：**装载区、缓存区、充电区、避让区**。不同区域的高频故障不同。

如果只做全局向量检索，会遇到一个问题：**跨区域共性故障互相污染**。例如「安全触边触发」在四个区域都有记录，全局检索会把其它区域的案例召回进来——区号不对、故障机理也可能不同，对运维是噪声。

### 3.2 策略

```
传入 area_id：
  ① 先在同区域案例内按相似度检索，取前 top_k；
  ② 同区域命中不足 top_k 时，从其它区域按相似度补齐；
  ③ 合并后整体按相似度降序重排。

不传 area_id：
  直接全局检索。
```

### 3.3 实测收益与代价

在 6 个跨区域共性故障上做 A/B 对照（A = 不知道区域，B = 知道区域）：

| 故障类型 | 跨区污染率 A | 跨区污染率 B | 相似度 A | 相似度 B |
|---|---|---|---|---|
| 碰撞触边类 | 0% | 0% | 0.6999 | 0.6999 |
| 急停锁止类 | 0% | 0% | 0.6940 | 0.6940 |
| 过载报警类 | **67%** | **0%** | 0.6097 | 0.4943 |
| 二维码丢失类 | 0% | 0% | 0.6361 | 0.6361 |
| 电池温度类 | 0% | 0% | 0.6919 | 0.6919 |
| 障碍物避让类 | **33%** | **0%** | 0.6003 | 0.5735 |
| **平均** | **17%** | **0%** | **0.6553** | **0.6316** |

**结论（需同时看两个指标）：**

- 跨区污染率 **17% → 0%**：召回结果全部来自正确区域
- 平均相似度 **-0.0237**：区域约束带来少量语义代价
- 个别情况下代价明显：过载报警类 top1 相似度从 0.7718 降到 0.5148，因为目标区域内没有语义最贴的记录

**所以不是"区域优先无条件更好"，而是：已知事件区域时用它降噪；不确定区域时用全局检索。**

## 4. 技术选型：一次实测驱动的模型替换

### 4.1 问题

最初使用 `all-MiniLM-L6-v2`（384 维，英文模型）。检索效果异常：**重新表述同一故障，召回结果会乱序**。

### 4.2 定位

打印分词结果后发现问题不在"语义能力弱"，而是**模型根本不认识中文**：

```
原模型（all-MiniLM-L6-v2，vocab 30522）
  '视觉幻视'          → ['[CLS]', '[UNK]', '[UNK]', '[UNK]', '[UNK]', '[SEP]']
  'relay protection'  → ['relay', 'protection']          ← 英文正常

词表里含中文字符的 token 仅 488 个，且全部是 '##一' 这类"接续子词"，
无法独立成词，因此中文全部退化为未知词 [UNK]。
```

模型实际拿到的是一串"未知符号"，检索排序接近随机。

### 4.3 替换与验证

换成中文优化的 **BGE-small-zh-v1.5**（512 维，vocab 21128，含中文 token 14642 个）：

```
BGE（bge-small-zh-v1.5）
  '视觉幻视'  → ['[CLS]', '视', '觉', '幻', '视', '[SEP]']   UNK = 0
```

**效果对比：**

| 指标 | MiniLM（原） | BGE（新） |
|---|---|---|
| 中文分词 | 全部 `[UNK]` | 逐字切分，0 个 UNK |
| 向量维度 | 384 | 512 |
| 正确项与最佳错误项的分差 | **+0.0002** | **+0.2087** |
| 初始化耗时 | 1942 ms | **724 ms** |

### 4.4 两个必须遵守的 BGE 约定

| 约定 | 说明 |
|---|---|
| **CLS pooling** | 取 `last_hidden_state[:, 0]`，不是 mean pooling |
| **查询前缀** | 查询需加 `为这个句子生成表示以用于检索相关文章：`，**文档不加** |

加错（例如给文档也加前缀）效果会显著下降。实现见 `bge_embedding.py`。

## 5. 安全设计：LLM 不得参与安全决策

这是工业场景的硬要求。项目在三个层面做了约束：

### 5.1 提示词层（软约束）

`agv_agent.py` 的 system prompt 中明确列出禁止事项：不得修改、建议修改、质疑风险等级与控制动作；不得输出任何新的控制指令。

### 5.2 代码层（硬约束）

`agent_harness.py` 在模型返回后扫描违规措辞，命中即判定输出不合格：

```python
FORBIDDEN_PATTERNS = (
    "建议停机", "建议立即停机", "建议断电", "可以恢复运行",
    "无需停机", "建议降级", "建议提高风险", "风险等级应改为", ...
)
```

不合格的输出会被拦截并替换为**只引用规则结论**的兜底报告。

### 5.3 架构层

`rule_risk` / `rule_action` 在整个链路中**只读**，仅作为文本透传。`agent_harness.py` 不提供任何修改它们的接口。

## 6. LLM 可靠性外壳（Agent Harness）

`agent_harness.py` 在"调用 LLM"外面加四层保障，上层业务零改动即可替换 `agent.analyze()`：

| 层 | 能力 | 说明 |
|---|---|---|
| ① 输出校验 | 违规措辞 + 三段结构 | 把软约束升级为可验证的硬约束 |
| ② 失败重试 | 指数退避 1s → 2s → 4s | 应对超时、网络抖动、空返回 |
| ③ 降级兜底 | 永远返回可读报告 | 不中断 AGV 主链路 |
| ④ 指标统计 | 耗时 / token / 成功率 / 降级原因 | 支撑成本核算与可用性监控 |

**输出预算也由 Harness 统一管控**（而不是写死在 agent 里）：

```python
harness = AgentHarness(
    max_retries=2,
    max_output_tokens=600,    # API 层硬上限
    max_report_chars=800,     # 软阈值，超长只告警不重试
)
```

### 性能优化实测

初版提示词只要求"每条尽量具体"，模型每次写 7 条详细步骤，单次约 1700 输出 token、耗时 10 秒。加入篇幅约束与 `max_tokens` 后：

| 指标 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| 单次 LLM 耗时 | 10655 ms | **1979 ms** | **5.4×** |
| 输出 token | 5361 | **697** | **7.7× 减少** |
| 报告字数 | 800~1200 | 354~450 | 更精炼 |
| 三段结构完整 | ✅ | ✅ | 保持 |

## 7. 实测结果

### 7.1 检索质量（3 组典型用例）

| 用例 | 查询 | 期望 | 实测 top1 | 结果 |
|---|---|---|---|---|
| 装载区视觉幻视 | 装载区AGV把货架看错了，出现幻视 | `fault_RAN_001` | `fault_RAN_001` (0.8314) | ✅ |
| 充电区电池高温 | 充电时电池温度过高报警 | `fault_RDA_001` | `fault_RDA_001` (0.7667) | ✅ |
| 避让区安全触边 | AGV撞到东西后触发安全触边 | `fault_RAB_002` | `fault_RAB_002` (0.7106) | ✅ |

全部为**改写后的查询**（非知识库原文），命中率 3/3。

### 7.2 风险决策

判据使用**最高相似度** `max_sim`（而非平均相似度）。原因：`top_k` 结果中除 top1 外多为无关记录，会拉低均值，导致"匹配最准反而判低风险"的反直觉结果。

| 查询 | max_sim | 风险等级 | 控制动作 |
|---|---|---|---|
| 装载区幻视 | 0.8314 | 高风险 | AGV立即暂停，人工确认现场 |
| 充电区电池高温 | 0.7667 | 中风险 | AGV减速运行，二次校验传感器数据 |
| 避让区安全触边 | 0.7106 | 中风险 | AGV减速运行，二次校验传感器数据 |

阈值按实测分布校准：`无匹配 < 0.45`、`中风险 ≥ 0.67`、`高风险 ≥ 0.78`。

### 7.3 运行指标

```
知识库案例    : 16 条（4 区域各 4 条）
向量维度      : 512
初始化耗时    : 460 ~ 724 ms
单次召回      : 8 ~ 15 ms
单次 LLM      : 1979 ms（平均）
LLM 成功率    : 100% (3/3)
Token 消耗    : 输入 3128 + 输出 697 = 3825
整体耗时      : 7408 ms（3 组用例）
```

### 7.4 成本估算

```
单轮 3 用例 ≈ 4200 tokens
按每天 30 起现场事件估算：年 ≈ 1500 万 tokens
DeepSeek 定价下年成本 ≈ 几十元人民币
```

## 10. HTTP 接口

`web_demo.py` 提供三个接口，详见 [docs/API.md](docs/API.md)。

| 方法 | 路径 | 说明 | 耗时 |
|---|---|---|---|
| GET | `/api/config` | 知识库概况、预置事件、阈值 | < 5 ms |
| POST | `/api/retrieve` | 召回 + 规则决策 | ~10 ms |
| POST | `/api/analyze` | 完整链路（含 LLM） | ~2 s |

**接口拆分的意义**：前端可以先拿到检索结果与安全结论立即展示，再异步等待 LLM。安全控制不被 LLM 阻塞。

## 14. 3D 仿真集成（CoppeliaSim，可选）

除 2D 俯视图外，项目还提供一个与 **CoppeliaSim** 联动的桥接器，用于在 3D 场景中演示"AGV 实际移动 → 触发区域故障分析"。

### 14.1 它做什么

```
CoppeliaSim 中的 AGV 移动（物理仿真）
        ↓  ZMQ，10Hz 轮询世界坐标
coppelia_bridge.py 判定 AGV 所在区域
        ↓  仅在「跨入新区域」时触发（带 0.3m 滞回与冷却）
按区域选取一条故障事件
        ↓
检索 → 规则决策 → LLM（经 Harness 校验）
        ↓
结果回写 CoppeliaSim：机器人变色 + 控制台日志
```

**分工原则**：AGV 的运动来自物理仿真（真实），故障事件按区域规则触发（确定），两者严格分离，不做随机造数。

### 14.2 环境准备

CoppeliaSim 4.10+ 的 macOS arm64 版本为原生构建，无需 Rosetta。

```bash
# 1) 安装 ZMQ 通信依赖（约 5 MB）
pip install pyzmq cbor2

# 2) 安装 CoppeliaSim 自带的 Python 客户端（离线，从 app 包内安装）
pip install "/Applications/coppeliaSim.app/Contents/Resources/programming/zmqRemoteApi/clients/python"

# 3) 启动 CoppeliaSim，打开含移动机器人的场景
#    默认使用 /dr12[0]，可用 --robot 指定其它对象
```

### 14.3 运行

```bash
# 一直运行，Ctrl+C 退出
python coppelia_bridge.py

# 定长运行（适合录屏），并调整触发冷却
python coppelia_bridge.py --duration 60 --cooldown 5

# 指定其它机器人对象
python coppelia_bridge.py --robot "/dr12[1]"
```

输出示例：

```
    12.2s  (  2.105,  0.319)  装载区       → 视觉幻视
```

### 14.4 两个工程细节

**① ZMQ 客户端非线程安全**
CoppeliaSim 的 REQ socket 不能跨线程使用。本桥接器的约束是：
- 主线程：全部 `sim.*` 调用（读位置、写颜色、写日志）
- 工作线程：只跑分析链路（纯 Python）
- 两者通过 `queue.Queue` 通信

早期版本用 `threading.Timer` 在子线程里恢复颜色，导致 socket 状态被破坏，运行一段时间后抛
`ZMQError: Operation cannot be accomplished in current state`。

**② 边界滞回（Hysteresis）**
AGV 停在区域分界线附近时，坐标抖动会导致"区域频繁切换"，把分析链路打爆。
实现上要求 AGV 距分界线超过 `0.3m` 才承认区域切换，否则沿用上一次结果。

### 14.5 与 2D 前端的关系

两者相互独立，可同时运行：

| | 2D 界面（`web_demo.py`） | 3D 桥接（`coppelia_bridge.py`） |
|---|---|---|
| 事件来源 | 手动点击 / 自动轮转 | CoppeliaSim 中 AGV 实际跨区 |
| 依赖 | 仅标准库 | 需要 CoppeliaSim + pyzmq |
| 用途 | 日常演示、接口调试 | 现场汇报的视觉增强 |

二者复用同一套分析链路（`web_demo.do_analyze`），因此阈值、重试、降级、指标完全一致。

## 15. 运营仿真与链路压测（可选）

`fleet_sim.py` 用离散事件仿真（SimPy）回答一个工程问题：**这套系统放在真实运营强度下表现如何？**

### 15.1 为什么需要

单点能力已完成（能分析一起故障），但落地要回答的是量级问题：

| 问题 | 需要的指标 |
|---|---|
| 能扛多少量？ | 吞吐量、任务周期 |
| 花多少钱？ | token 消耗、年化成本 |
| 可靠吗？ | 成功率、延迟分位数 |
| 瓶颈在哪？ | 资源利用率、排队时长 |

### 15.2 两阶段设计（关键）

```
阶段一：运营仿真（SimPy）          阶段二：链路压测（真实调用）
  8 台 AGV 任务流转                  42 起事件逐条送入
  充电桩排队                         向量检索 → 规则决策 → LLM
  按区域泊松过程注入故障             记录真实延迟与 token
        ↓                                  ↓
  【运营指标】模型估算              【分析指标】真实测量
```

**两类指标来源严格分开**，避免把仿真数字误当实测数据。

这个设计本身还验证了一个架构判断：

> **LLM 不在安全回路里，所以它的延迟不影响运营。**
> 阶段一的 24 小时运营时间推进，与阶段二的约 2 分钟 LLM 耗时完全独立。

### 15.3 实测结果

```
【运营】（模型估算，固定种子 42）
  完成任务数      : 3477 个
  平均任务周期    : 2.2 分钟
  AGV 利用率      : 79.4%
  充电桩利用率    : 50.7%
  平均充电等待    : 0.3 分钟

【故障流】
  事件总数        : 42 起/天（1.75 起/小时）

【分析链路】（真实测量）
  成功率          : 100%（42/42）
  召回延迟        : P50 19.2ms / P95 186.8ms
  LLM 延迟        : P50 2.17s / P95 4.18s / P99 7.27s
  Token           : 62,049（单次平均 1,477）
  年化成本        : ≈ ¥18
```

### 15.4 What-if：用仿真做决策

```bash
./run.sh sim --what-if
```

```
  充电桩   完成任务   利用率    平均排队   最长排队
    1      3317     97.2%     7.5 分    30.2 分   ← 明确瓶颈
    2      3477     50.7%     0.3 分     4.8 分   ← 拐点
    3      3490     34.3%     0.0 分     0.0 分   ← 收益递减

边际收益：1→2 吞吐 +4.8%；2→3 仅 +0.4%
建议：2 个充电桩，继续扩容不值得
```

**结论不是"越多越好"，而是找到拐点。** 这才是仿真作为决策工具的价值。
